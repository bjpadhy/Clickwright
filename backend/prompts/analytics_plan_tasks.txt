<rules>
1. One to four tasks. Each is exactly one aggregate query's worth of work — if a task
   needs two GROUP BYs to answer, it is two tasks.
2. Name the tables each task reads, from the list above only.
3. Apply the store's metric definitions verbatim, including denominators.
4. Cut by the dimensions the question implies (platform, geo, destination, time) and
   nothing more. Breadth costs accuracy: three focused tasks beat four vague ones.
5. Every task returns sample sizes alongside rates.
6. If the question is comparative ("vs", "lift", "which is worst", "how much faster"),
   one task must compute that comparison as a column — a delta the SQL does not produce
   can never be reported.
6b. For funnel or multi-step questions ("conversion from X to Y to Z", "where is the
   biggest drop-off"), plan tasks so a later task can `depends_on` an earlier one.
   The dependent task will receive the earlier task's result summary, letting it
   reference concrete counts for drop-off computations.
6c. For GLOBAL questions with no dimension specified ("what's our conversion rate?",
   "how many users paid?"), always include at least one task that breaks the metric
   by the most likely explanatory dimension (typically os or geoip_country_code).
   A global number that hides a 4× gap between platforms is a bad answer. State in
   `approach` that you are proactively segmenting.
7. A follow-up that recomputes a quantity already reported above must recompute it the
   SAME way — same denominator, same population, same filters. Say which denominator in
   the task's `question` so the SQL step cannot drift ("conversion over pay_now_clicked
   applications, as already reported"). The `n` beside each figure identifies its
   population: plan for the same n. If the new question genuinely needs a different
   basis, plan for it AND say in `approach` that it differs, so the answer can explain
   the change rather than silently contradicting the earlier number.
8. If the question cannot be answered from these tables, return zero tasks and explain
   why in `approach` — naming what data would be needed. That is a valid, useful
   answer, and far better than tasks that compute an approximate stand-in for it.
   If the question is ambiguous in a way that changes the answer, say so in `approach`
   and plan for the most defensible reading rather than silently picking one.
9. List in `assumptions` every choice the question left open that changes the number
   and that you made for it: which stored metric, its denominator, the time window,
   the segment or population, the definition of an event. One short phrase each
   ("last 90 days", "denominator = pay_now_clicked applications", "all platforms"),
   at most six, and nothing the question already states. An EMPTY array is right
   when the question pins these down — never pad it. No figures beyond the window
   itself: each assumption is reported to the user as a deduction from the answer's
   confidence, so it must name a choice, not a result.
9b. A metric definition in the knowledge block fixes its own denominator and its
   filters. If the question names that metric, those are PINNED, not assumed — do
   not list them. "denominator = pay_now_clicked applications" beside a question
   asking for the standard checkout conversion rate is not a choice anyone made;
   the definition made it. List only what is still open after the definition is
   applied, which is usually the time window and the segment.
9a. Every assumption must be one the tasks ACTUALLY APPLY. If you assume a time
   window, the task's `question` has to state it so the SQL filters on it — an
   assumption of "last 90 days" beside a query with no date predicate tells the

   than saying nothing. Either filter on it or do not claim it. The same holds for
   a segment or a denominator. Do not carry the example's window across: it is an
   illustration of the FORM, not a default to apply.
</rules>
