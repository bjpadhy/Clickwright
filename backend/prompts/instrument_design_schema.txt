<coherence>
You are designing a SET of tables, so decide these ACROSS the whole feature, not table
by table:
- **Shared columns get one type.** A column that appears in several events (an id, a
  channel, a status) must have the SAME type everywhere, or joins and UNIONs silently
  cast or fail. Pick the type from the union of all measured values.
- **Join keys must be comparable.** If table A joins table B on a key, that key must be
  the same type in both, and should lead A's ordering key where A is filtered by it.
- **Consistent enum members.** If two events carry the same categorical column, their
  Enum8 must list the same members in the same order, or the values mean different
  things in each table.
- **Note the funnel.** The spec names an event order; say which column links the stages
  so the analytics agent can join them without guessing.
</coherence>

<design_rules>
**Ordering key** — the single highest-impact choice, and **immutable**: it cannot be
changed later without rebuilding the table, so get it right now
(`schema-pk-plan-before-creation`). Lead with the columns that appear in WHERE clauses
for the PM's questions (`schema-pk-prioritize-filters`), ordered LOW cardinality first
(`schema-pk-cardinality-order`): the sparse index works on granules, so low-cardinality
leading columns let whole blocks be skipped, while a high-cardinality id first prunes
almost nothing. Put the join key and timestamp after. Justify from measured distinct
counts.

**Types** — narrowest correct type from the measured range:
- Prefer `LowCardinality(String)` over `Enum8` for ALL categorical columns. Enum8
  validates on insert, which means a new value in future data causes a HARD INSERT
  FAILURE — unrecoverable without an ALTER. LowCardinality(String) is nearly as
  compact (dictionary-encoded, ~1 byte per value for small sets) and handles new
  values gracefully. Use it for status, channel, platform, method, and any string
  with fewer than ~10K distinct values (`schema-types-lowcardinality`).
- Integers: UInt8 < 256, UInt16 < 65536, UInt32 < 4.29e9, else Int64/UInt64.
- Money: `Decimal64(2)` — Float64 causes rounding errors on aggregation.
  Other decimals (latency, scores): Float64. Timestamps: `DateTime64(3, 'UTC')`.
- Identifiers (user_id, application_id, share_id, uuid-like): plain String, never
  LowCardinality — high cardinality makes the dictionary a liability.
- Any field with a measured null/empty rate: `DEFAULT ''` (or 0), never Nullable —
  Nullable costs a separate mask column and blocks some optimizations.

**Codecs** — this is where most of the storage win is:
- Timestamps: `CODEC(Delta(8), ZSTD(1))` — monotonic values compress enormously.
- Integer measures with modest range: `CODEC(T64, ZSTD(1))`.
- Identifiers and free text: `CODEC(ZSTD(1))`.
- Do NOT add a codec to Enum8 or LowCardinality columns — already compact.

**Partitioning** — partitioning exists for **data lifecycle** (dropping or moving whole
partitions), not for query speed; the ordering key handles pruning
(`schema-partition-lifecycle`). Use `PARTITION BY toYYYYMM(timestamp)` and keep total
partition cardinality in the hundreds (`schema-partition-low-cardinality`) — finer
granularity causes part explosion and "too many parts" errors.

**Skip index** — add at most one, and only for a high-cardinality column the PM's
questions filter on that is NOT in the ordering key:
`INDEX idx_<col> <col> TYPE bloom_filter(0.01) GRANULARITY 4`.

**TTL** — only if the conventions or spec state a retention rule. Otherwise omit.

**Comments** — every column: the semantic meaning (what the values mean, units,
gotchas) in ≤ 12 words. Table comment ≤ 20 words: the event, its funnel role, the spec.

**Column clause order** — ClickHouse is strict and this order is verified against the
server: `\`name\` Type [DEFAULT expr] [COMMENT '...'] [CODEC(...)]`.
The COMMENT comes BEFORE the CODEC. Putting CODEC first is a syntax error.

Hard constraints: one CREATE TABLE per event type, named exactly after the event; ENGINE = MergeTree; every profiled field
becomes a column with its exact name; never invent or drop a column; escape single
quotes in comments by doubling (''); no SETTINGS clause (index_granularity and friends
are rejected by the server here — the defaults are correct).
</design_rules>

<example>
A measured profile of: timestamp (2.1k distinct) · user_id (1.6k distinct, 0% null) ·
status (3 distinct) · channel (4 distinct) · latency_ms (range 12–3999) · amount (money)
should produce:

CREATE TABLE example_event (
  `timestamp` DateTime64(3, 'UTC') COMMENT 'event time, ms precision' CODEC(Delta(8), ZSTD(1)),
  `os` LowCardinality(String) DEFAULT '' COMMENT 'empty on ~7% of rows, bucket as unknown',
  `status` LowCardinality(String) COMMENT 'application status when the event fired (3 values)',
  `channel` LowCardinality(String) COMMENT 'share channel: whatsapp, copy, email, sms',
  `user_id` String COMMENT 'traveller id, 28 chars, joins every table' CODEC(ZSTD(1)),
  `latency_ms` UInt16 COMMENT 'client-measured latency in milliseconds' CODEC(T64, ZSTD(1)),
  `amount` Decimal64(2) COMMENT 'value in the accompanying currency, never summed across currencies'
) ENGINE = MergeTree
PARTITION BY toYYYYMM(timestamp)
ORDER BY (status, channel, user_id, timestamp)
COMMENT 'example_event: a traveller shares status; step 1 of the sharing funnel (spec 03)'

The ordering key is the point: the two low-cardinality filters lead (3 and 4 values,
so granules prune cheaply and compress well), and the high-cardinality id plus
timestamp follow. Enum8 for the closed 3-value set, LowCardinality for the open one.
</example>

If the profile is internally inconsistent or a field's type cannot be determined
safely, choose the WIDER, safer type and record why in `deviations` — never guess a
narrow type to look precise. A schema that loses data is unrecoverable; a slightly
wide column is not.
